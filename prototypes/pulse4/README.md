# PULSE//4 — a tracker whose sound engine is a PDP-1

Four voices, square waves, per-voice pattern banks and order lists. The audio is
not synthesised: the app runs Peter Samson's Music 13 player (`pdp1m13`, 1962)
unmodified inside a cycle-accurate PDP-1 emulator, and the four program flags
*are* the output.

Everything here was built in one session with Joe Lynch, on top of his
[`pdp-1-boc`](https://github.com/joeblynch/pdp-1-boc) and
[`harmony-compiler-2`](https://github.com/joeblynch/harmony-compiler-2).
The emulator core is ported from `harmony-compiler-2/src/pdp1/*.ts`; the
embedded `pdp1m13.rim` is that repo's tape. Neither repo is vendored here.

Open `app/pulse4-pdp1.html` in a browser. Nothing to install.

## How it works

The tracker does **not** emit a Harmony Compiler intermediate tape. It emits the
*compiled event stream* — the two-word segments HC's second pass would have
produced — and deposits them into core banks 1–2. A three-word stub
(`jsp tun` / `eem` / `jmp pla`) hands control to the 1962 player.

```
word 1 : [pitch v1 :6][pitch v2 :6][pitch v3 :6]
word 2 : [loopct/2 :12][pitch v4 :6]
```

Note the asymmetry — `cc4` builds word 2 with a `rcr 6s` chain that rotates
pitch 4 in *first*, so the loop count ends up in the **high** 12 bits. Getting
this backwards was the first real bug.

- One tracker pattern = one bar. HC's bars-list is already an order list, so
  the mapping is one-to-one.
- Pitch index = MIDI − 22. Index 0 = rest, 1 = B0 (reachable by direct event
  authoring but not by the score language), 63 = C#6.
- Segment wall time = `(loopct/2 + 1) × 350 µs`.
- Capacity: 3646 segments across banks 1–2. Olson dry is 116 (3.2%).

## Findings worth carrying back

**`dap` is mistimed in `harmony-compiler-2/src/pdp1/cpu.ts`.** It is charged
`MEMT * 2` on top of the instruction fetch (15 µs); on the PDP-1 it is an
ordinary memory-reference instruction at 10 µs, like `dac`. `nxt` contains four
`dap .+1`, one per voice, so the fetch cost 370 µs instead of the 350 µs the
block diagram states — and a segment split was paying 350 µs of phase against
370 µs of wall time, so splitting a long note was not quite phase-neutral.
With `dap` corrected, `nxt` measures 350 µs exactly and renders land on the
predicted duration regardless of segment count. See `tests/timing-nxt-lup.js`.
The app has the fix; upstream does not.

**`tun` never runs on the read-in path**, only on the Start dispatch. Straight
after `readIn` the tables at 300–677 are zeros and the machine is silent.

**`tuw` packs two unrelated things**: four 3-bit per-voice fields *and* a 6-bit
global bias, as `1 + ((field − 4) + 2·bias)/512`. Stock `642017` is a ±19.2¢
spread riding on a **+95.3¢ global bias**. Against the CHM clock's −133.9¢ that
lands A4 at **430.31 Hz** — the machine is about a third of a semitone flat of
concert, near Baroque pitch. The bias is not shimmer; it is where the tuning
lives. (An early "DETUNE: NONE" preset zeroed the whole word and dropped the
instrument 95¢. Fixed: "NO SPREAD" keeps the bias.)

**Pitch modulation is free of clicks.** `nxt` rewrites `f1–f4` and never touches
the phase accumulators or any envelope, so stepping a held note between pitch
slots is a glide, not a retrigger.

## Live editing

The stream layout is a function of (song, tempo, rows, drift grid) only. Rate,
depth, shape, seed and per-voice settings change *which slot* each segment
points at, never the loop counts — so they are patched into core in place while
the machine runs, and `writeStreamPitches` rewrites word 1 whole and only the
low 6 bits of word 2. Segments already fetched keep their old value until the
stream loops, which is exactly "from the playhead forward".

Depth, temperament and tuning don't touch the stream at all — only the pitch
tables. Structural changes (a note, the tempo, the grid) rebuild and drop the
cursor back at the same tick.

The machine runs in a ScriptProcessorNode at about **1.2% duty** — 67 ms of work
for 5.6 s of audio.

## Drift

Spare pitch-table slots hold detuned copies of the pitches actually in play, and
the event stream walks long notes through them. Olson uses 6/4/4/6 of each
voice's 64 slots, leaving room for ±4/±7/±7/±4 steps. Cost is set by the GRID
control (events/sec), not by the rate.

## Known limits

- Notes clamp to B0–C#6; out-of-range ones show red in the grid.
- Changing ROWS stops playback (the tick basis changes).
- WAV export stops the machine and renders offline.
- The exported `.rim` is emulator-verified only — never run on hardware. It
  carries all four pitch tables verbatim rather than calling `tun`, so it is
  self-describing but ~29 ft of tape for Olson instead of ~16.
- The emulator mixes v2 and v4 at negative gain, so same-phase pairs partially
  cancel. That is upstream behaviour, preserved deliberately; the open question
  about hardware polarity in `IDEAS.md` is untouched.
